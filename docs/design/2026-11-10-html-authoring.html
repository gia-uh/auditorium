Auditorium 5: authoring in HTML, CSS and JS, with a Python CLI that checks, bundles, presents and renders

docs/design/2026-11-10-html-authoring.html·proposal, closes #100·replaces the authoring half of 2026-11-05-agent-first-artifacts.html

Auditorium stops being a Python API for writing decks. A deck, a poster, a short video or a page is a folder of plain HTML, CSS and JS, started from one of auditorium's templates and styled with its stylesheet and motion library. The Python package becomes the tool around those files: it scaffolds them, explains them, checks them with rules written for small models, bundles them into one file, presents them live and renders them to video, PNG and PDF. deck.py is removed.

01What this delivers

Authoring an agent already knows

HTML with a few data- attributes for time and motion. A file opens in a browser as it is, with no build and no Python to run. Any model writes HTML; few write async timeline code well.

A CLI that knows everything

auditorium help and auditorium template carry all the knowledge an agent needs, versioned with the package. An agent with a shell and this CLI needs no other doc, skill or prompt.

Checks a small model can act on

Each finding names the file, the line, the rule and the edit that fixes it. Errors come first and few at a time, so a model with a short context fixes one thing per round instead of drowning.

03How it fits

The parts that survive from 4.x are the ones that never cared how the timeline was made: engine.js (seek over getAnimations(), forward replay, anchors), client.js (what the three browser surfaces share), the server's presenter and audience sync, the relay, the render schedule and the Playwright capture. What changes is the source of the timeline: the DOM instead of compiled Python.

04The project

# auditorium template new short launch --theme vivid
launch/
  index.html          # the artifact: what the author edits
  theme.css           # CSS variables only: palette, fonts, radii, grid, type scale
  script.js           # optional: auditorium.track() functions, data for charts
  assets/             # images, logos, audio, narration clips and their alignment JSON
  auditorium.toml     # format, language, reading rate, check overrides; written by template
  README.md           # the template and version it came from
  dist/               # bundle, render and export write here; never edited

Live data: a [data] table in auditorium.toml names each endpoint a page may fetch and the fixture file that stands in for it during check, render and export. The bundle keeps the fetch, so the published page shows current data; a video or PDF shows the data at the time it was made.

index.html loads auditorium.js and auditorium.css from a path the CLI serves, so the file opens in auditorium preview without a copy of the runtime in every project. bundle is what puts the runtime inside. A template carries its own example/, a finished artifact that passes the check with zero findings; CI checks every one.

05The file contract

<main class="aud" data-format="short">                 <!-- deck | square | portrait | story | short | explainer | page -->
  <section data-beat="hook" data-d="4.5" data-say="assets/vo/01.json">
    <div class="grid">
      <h1 data-col="1/13" data-enter="words" data-cue="a ball">A ball rolling downhill</h1>
      <div class="stat" data-col="1/7" data-in="2.2" data-enter="count">
        <b data-to="0.01">0</b><span>learning rate</span></div>
    </div>
    <audio src="assets/bed.mp3" data-in="0" data-gain="0.5" data-duck></audio>
  </section>
</main>
AttributeMeans
data-formatStage size, safe area, duration bounds, minimum type size and default outputs, as in the 2026-11-05 spec's format table. page is new: no stage, it flows at any width (reports, dashboards).
data-beat, data-dA section is a beat: a slide in a deck, a scene in a video. data-d is its length in seconds; in a presented deck it is omitted and the presenter advances.
data-stepPresented decks: the element appears at the Nth press inside its slide, as 4.x beat() did.
data-in, data-outSeconds from the start of the beat. Omitted means the whole beat.
data-cueInstead of data-in: the time the phrase starts in the beat's narration (data-say, clip plus alignment JSON, #73).
data-enter, data-exit, data-idleNames from the motion library: rise, fade, words, pop, flip, draw, grow, count; idles float, tilt, ken-burns, pulse. Optional data-dur and data-ease; the defaults are tuned once.
data-col, data-rowPlacement on the format's grid. The grid rule checks these elements and ignores inline text.
data-placeholderSet by templates on content the author must replace; the check fails while it remains.

The runtime publishes what it built, for the CLI and for any other tool:

window.auditorium = { version: 5, format, stage: {w, h} | null, grid, beats: [{id, t, d, steps}],
                      duration, audio: [{src, t, gain, duck}], seek(t), goto(beat, step), ready }

Its shape is close to HyperFrames' window.__hf (duration plus seek) on purpose, so a tool written for one can be adapted to the other with a few lines.

06The runtime

  • Build: at load, auditorium.js walks the DOM once, turns each timed element into the same ops and tracks that 4.x compiled in Python, and creates every animation paused with fill: both (D3).
  • Seek: engine.js unchanged in substance: apply ops up to t, pin every animation in getAnimations() to t (D4), run tracked functions, resolve anchors with reads batched before writes (D6), replay forward after a backward seek (D5).
  • Custom code: auditorium.track(fn, {from, to}) registers a function of t; auditorium.rng(seed) replaces Math.random. A third-party library joins through an adapter with the HyperFrames shape: duration and seekFrame.
  • Library: auditorium.css holds the layouts (title, statement, cards, stats, two columns, figure, logo row, photo with caption, table, chart), the components, the motion keyframes and the background and grade layers from the 2026-11-05 inventory. KaTeX, highlight.js and the fonts stay vendored: math in <span class="math">, code in <pre data-lang>.
  • Chrome: keyboard and touch navigation, fullscreen, the presenter view and the audience mode come from client.js, the same in run and in a bundled file. Audience sync needs run; a bundled file navigates alone.

Editing in preview

  • Text: a click on any text element makes it editable (an overlay for SVG text, where contenteditable is unreliable). On commit the page posts the element's source position and the new text; the server replaces exactly that text range in index.html and leaves every other byte alone.
  • Attributes: a selected element shows its data- attributes as fields, with the valid names for data-enter and friends as choices, and its time on the scrubber as handles for data-in and data-out.
  • Theme: the variables of theme.css with colour pickers and number fields.
  • Source: a pane with index.html, theme.css and script.js, saved on demand.
  • Each write reloads the page at the same time and runs the structure pass of the check, so a broken edit shows at once. --edit is off by default, and the server refuses writes outside the project folder.

An app that embeds Auditorium can put this preview behind its own URL instead of writing an editor.

Every command takes --json, never prompts, and ends on one count line, so an agent can tell success from failure without parsing prose. A music bed from Euterpe stays an optional extra: auditorium music --mood calm --bpm 100 --length 30 -o assets/bed.wav writes a file like any other asset.

08The check

auditorium check runs in three passes, cheapest first, and stops reporting after the first pass with errors: a structural error makes geometry findings noise. The served copy of index.html gets a data-aud-line on every element from a position-tracking parser, so a finding found in the live DOM still points at a line of the file the author edits.

Written for small models

  • Each finding carries the rule, the line, the element's selector, the beat and time, what was measured against what, and the edit that fixes it in the file's own terms ("set data-col="1/13"", not "reduce width").
  • The text output shows the first 8 errors, grouped by line, then the counts. The full list is in dist/check.json. One identical finding over 40 sampled frames is reported once with its time range.
  • auditorium help rule NAME shows the rule with a broken and a fixed snippet.
  • Every rule has a fixture that breaks it in tests/rules/, and the suite fails if a rule does not fire on its fixture or fires on any template example.

13The eval

#81 stays as written in the 2026-11-05 spec, retargeted at HTML: twelve briefs (four decks, four posters, four shorts, two of them narrated) with their own assets and pre-made clips, a weak open-weight model and a strong one with the same CLI and nothing else, three runs each. The weak reference is Qwen3.6-27B through a coding-agent CLI. Measures: delivered, zero check errors, must-include facts found as text, check rounds, tokens and wall time; blind pairwise preference by a person, with a vision model as second judge. Target for 1.0 unchanged: the weak model delivers every brief with zero errors and wins or ties in at least 40 % of comparisons.

The baseline runs at the end of M2, when the first templates and the check exist. A baseline on the 4.x API would measure something that will no longer ship.

15Non-goals and open questions

Non-goals

  • A Python authoring API, a shim for deck.py, or a converter from it.
  • A layout editor (drag, resize, a timeline editor). Preview edits text, attributes, theme variables and the source.
  • Calling TTS, image services or any network from a command other than assets. The check serves declared data endpoints from their fixtures.
  • Node or npm as a dependency.

Open questions

  1. Algorithm visualisations were the reason to allow arbitrary Python inside an animation. In HTML they become track() functions in JS, or a script that writes the HTML. Is that enough for that audience, or does it need a data-driven component (steps from JSON)?
  2. Anchored arrows between boxes (D6) as a custom element, <aud-arrow from to>, or as attributes on an SVG path?
  3. Should check --fix apply the mechanical fixes (nearest valid name, a missing data-d from reading time), or should the model always make the edit itself?
  4. Where the runtime lives for index.html during authoring: served by the CLI (proposed), or copied into each project so the file opens with a double click.
